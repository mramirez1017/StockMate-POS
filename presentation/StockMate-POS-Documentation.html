StockMate POS — Inventory & Point-of-Sale Platform

Complete developer documentation for the StockMate POS system: the web back office, the Android app, the Firebase Cloud Functions backend, and the shared data model.

Built by AMDev Studio Firebase project: stockmate-pos Live web: stockmate-pos.web.app Generated June 18, 2026

1What this app is

StockMate POS is a multi-tenant, multi-branch inventory and point-of-sale platform. One codebase serves several audiences from one cloud backend:

  • Web back office — a React app where store owners and managers run inventory, purchasing, transfers, approvals, reports, and user management from any browser (desktop or tablet).
  • Web POS — the same app's checkout screen for selling at a counter.
  • Android app — a Jetpack Compose app for mobile POS, barcode scanning, receiving deliveries, stock counts, and transfers on the shop floor.
  • Platform console — a super-admin area (Stores, Analytics) for the platform owner who provisions stores.

Every surface connects to one cloud backend (Firebase). Reads are live; sensitive writes go through Cloud Functions, so a sale, transfer, or price change reflects across every screen and branch within about a second.

2Architecture overview

Unlike a simple "browser writes directly to the database" app, StockMate routes all business-critical writes through Cloud Functions running the Firebase Admin SDK. Clients only read directly (guarded by Security Rules) and subscribe in real time with onSnapshot. This keeps stock math, approvals, and audit trails authoritative and tamper-proof.

5Multi-tenant model: stores & branches

StockMate is multi-tenant. Each store is an isolated tenant; almost all data lives under stores/{storeId}/…. A store has one or more branches, and most operational records carry a branchId so inventory and reports can be scoped per branch.

flowchart TB PO["platformOwners/{uid}"] -."provisions".-> S IDX["userStoreIndex/{uid}
maps a login → its storeId"] --> S RE["registeredEmails/{emailKey}
pending invites"] -.-> S subgraph S["stores/{storeId}"] direction TB U["users/{uid}"] B["branches/{branchId}"] P["products / categories / suppliers"] INV["branchInventory (per branch & product)"] OPS["sales · stockMovements · transfers · counts · POs …"] end
Three top-level helper collections route a login to its tenant; everything else is nested under the store.

Client queries are branch-scoped (see web/src/lib/branchScope.ts): store-wide roles (owner/admin/platform owner) see all branches; managers and cashiers are limited to their assigned branchId.

6User roles & permissions

Roles are defined in @stockmate/types as UserRole:

RoleScopeWhat they can do
PLATFORM_OWNERAll storesPlatform super-admin. Provisions stores, sees the Stores & Analytics console. Tracked in the top-level platformOwners collection.
ADMIN (Store Owner)One store, all branchesFull control of a store: products, prices, approvals, users, reports. Approves manager requests.
STORE_MANAGEROne branchRuns a branch: stock, receiving, requests transfers/adjustments, branch-scoped reports.
CASHIEROne branchPOS & receipts, product search, returns within policy. May request extra permissions.

Granular permissions

On top of roles, individual users can be granted flags (CustomPermissions): canVoidSale, canApproveStockAdjustment, canViewSupplierCost, canCreatePurchaseRequest, canChangePrice. Managers/cashiers can request any RequestablePermission; an admin approves it (see §18).

Role checks are enforced twice: in the UI (route guards, hidden buttons) and on the server (Cloud Functions + Security Rules). The server is the source of truth.

7Authentication & user onboarding

There is no public self-registration into a store. Access is invitation-based: an admin registers a staff email, the person signs in with that email, and the account is claimed and linked to the store with a role and branch.

Invitation-based onboarding — handled by the user callables (Admin SDK).
  • Login is shared at /login; after sign-in the app routes by role (HomeRedirect). Deactivated accounts (status != ACTIVE) are blocked.
  • Role / permission changes go through updateUserRole and setUserPermissions callables and reflect live.
  • Deactivate a leaver with deactivateRegisteredEmail; access is revoked while history is preserved.
  • Relevant callables: registerUserEmail, claimAccount, updateUserRole, setUserPermissions, deactivateRegisteredEmail, repairPlatformOwnerSession.

11Inventory & stock movements

Stock is stored in pieces per branch in branchInventory. Every change writes an immutable stockMovements record, typed by StockMovementType:

MovementTriggered by
DELIVERY_RECEIVEDReceiving a purchase order delivery
SALEA completed POS sale (stock out)
RETURNA sale return / refund restocking good items
DISPOSALDamaged / expired stock written off
ADJUSTMENTApproved manual correction or stock-count variance
TRANSFER_OUTStock leaving the source branch on a transfer
TRANSFER_INStock arriving at the destination branch

Reorder & critical thresholds drive status colours and alerts; the criticalStocks collection is maintained by functions for fast dashboards.

12POS & sales

The POS supports barcode scan or live search, split payments, manual discounts (permissioned), held/parked carts, and printed/emailed/SMS receipts. A sale is created atomically by createSale.

flowchart LR C["Cashier builds cart
(scan / search)"] --> P["Apply promo / discount
split payment"] P --> S["createSale() · transaction"] S --> S1["decrement branchInventory"] S --> S2["write sale + SALE movements"] S --> S3["refresh dashboardStats
+ criticalStocks"] S --> R["Receipt: print / email / SMS"]
A POS sale is one atomic transaction; stock and stats update everywhere instantly.

Voids & returns: a cashier can request a void (voidSale) which an admin approves (approveSaleVoid) — or process a partial/full return (createSaleReturn) that restocks good items. Sale state follows SaleStatus: COMPLETED → VOIDED / REFUNDED / PARTIALLY_REFUNDED.

14Stock transfers (branch-to-branch)

Managers request transfers; admins approve and dispatch. An admin-initiated transfer is auto-approved. The receiving branch sees it as an incoming delivery (dashboard + Upcoming Deliveries) and completes it.

Transfer lifecycle (StockTransferStatus). OUT happens at approval; IN happens at receipt.

15Stock counts (cycle counts)

A physical stock-take session snapshots expected quantities, the counter enters physical counts, and submitting posts an ADJUSTMENT movement for every non-zero variance — so the books match the shelf.

flowchart LR N["createStockCount()
FULL or PARTIAL · snapshots expected"] --> P["IN_PROGRESS
enter counted qty"] P --> S["submitStockCount()
posts variance adjustments"] S --> D["COMPLETED"] P --> X["cancelStockCount() → CANCELLED"]
Status: StockCountStatus = IN_PROGRESS · COMPLETED · CANCELLED; scope = FULL | PARTIAL.

16Auto-reorder & critical stock

Items at or below their critical threshold can generate a draft purchase order via generateReorderDraft, grouped by supplier, so best-sellers don't run dry. Low/critical alerts are pushed as notifications with deep links to the affected item.

17Units & packs (buy in boxes, sell in pieces)

Stock is always counted in base units (pieces). A product can define a purchase pack with unitsPerPack (e.g. 200) and a packLabel (e.g. "box"). The pack is a purchasing/receiving convenience only:

  • Receiving accepts a quantity in boxes and multiplies into pieces.
  • Supplier cost is entered per box and stored per piece (boxCost ÷ unitsPerPack) for valuation/COGS.
  • Displays show the remaining packs — e.g. = 3 boxes + 30 pcs, or ≈ 0.5 box left when under one box.

Helpers live in web/src/lib/productUnits.ts (formatPackNote, formatPackBreakdown, piecesToPacks) and on the Android Product model (packNote()).

19Notifications & messaging

  • In-app notifications (notifications) are per-recipient, written only by functions, with unread badges and deep links (e.g. to a transfer, return, or count). A user can only read notifications addressed to their own uid.
  • Threads & messages power staff conversations (admin ↔ manager ↔ cashier), scoped by branch or explicit participants. Writes go through sendMessage / unsendMessage / markThreadRead.
  • Receipts can be emailed (sendReceiptEmail) or sent by SMS (sendReceiptSms).

20Reports, dashboard & analytics

  • Dashboard — today's sales, transactions, low & critical stock, upcoming deliveries and incoming transfers; backed by dashboardStats for speed.
  • Reports — inventory valuation & COGS, stock-aging / dead-stock, stock movement history, top sellers, with branch & date filters.
  • Platform analytics — cross-store metrics for the platform owner.
  • Tables across the app use a shared DataTable with sorting and Pagination (25 rows/page by default).

22Security model

Enforced by firestore.rules. The guiding principle: clients read (guarded), functions write. Helper functions resolve the caller's store and role from userStoreIndex + stores/{storeId}/users/{uid}.

CollectionReadWrite
products, categoriesStore users / platform ownerAdmin (direct)
suppliers, promosStore usersAdmin
purchaseOrdersStore usersManager+ (create/update); admin delete
branchInventory, sales, stockMovements, stockTransfers, stockCounts, deliveryReceipts, saleReturns, parkedSales, disposals, criticalStocks, notificationsStore users (notifications: own only)false — functions only
stockAdjustmentsStore usersManager+ create; update false
auditLogs, dailyReportsAdmin / manager+false
threads / messagesAdmins, or participants / same branchfalse
Role helpers in rules: isStoreUser, isAdmin (OWNER/ADMIN), isManagerOrAbove, isPlatformOwner, plus sameBranch() for branch scoping.

23Real-time sync

Clients subscribe to Firestore with onSnapshot, so a write from any surface (web POS, Android, another branch) appears everywhere within ~1 second — no redeploys for data changes. Lists are branch-scoped client-side via branchScopedQuery and role helpers (isStoreWideAccess).

24Setup & local development

Prerequisites: Node.js 20 (LTS), npm, and the Firebase CLI (npm install -g firebase-tools). Android also needs Android Studio + JDK.

# from the repo root — install all workspaces
npm install

# build the shared types first (web & functions depend on it)
npm run build -w @stockmate/types

# run the web app locally
npm run dev -w web

25Build & deploy

Always build shared/types before functions / web. On Windows PowerShell, chain steps with ; (not &&).

# 1) shared types → 2) functions → 3) web
npm run build -w @stockmate/types
npm run build -w functions
npm run build -w web

# deploy
firebase deploy --only hosting                 # web only
firebase deploy --only functions               # backend only
firebase deploy --only firestore:rules         # after editing firestore.rules
firebase deploy                                # everything
Project & hosting target: stockmate-pos (see .firebaserc). The Android APK is built separately in Android Studio.

26Maintenance checklist

  • Catalog — keep products, prices, supplier costs, reorder/critical levels, and pack sizes current.
  • Operations — review purchase requests, approve transfers/adjustments, receive deliveries, run periodic stock counts.
  • Users — invite/deactivate staff, set roles & permissions, action access requests.
  • Content — promos and store settings (tax, currency, receipt header/footer).
  • Cloud — Firebase handles servers, scaling, and backups; monitor the functions quota on heavy deploys.

27Frequently asked questions

Q: Why can't the client write inventory directly?
To keep stock math, approvals, and the audit trail authoritative. Operational collections are write:false in rules and only mutated by Cloud Functions running the Admin SDK.

Q: I changed a product but a sent quote/sale didn't change.
Sales store their own line snapshots; later catalog edits never alter historical records.

Q: A manager can't approve a transfer.
Approval is admin-only (isAdmin: OWNER/ADMIN). Managers request; admins approve.

Q: How do I make someone an admin?
Change their role via the Users screen (updateUserRole), which writes role: ADMIN on their store user doc. There is no public admin sign-up.

Q: Can a cashier see another branch's stock?
No. Queries are branch-scoped and rules restrict store users to their branch unless they're store-wide (owner/admin).

Q: How are boxes handled for medicine-style goods?
Define unitsPerPack; stock stays in pieces, receiving accepts boxes, and displays show packs left. See §17.

28Troubleshooting

SymptomLikely cause / fix
"Missing or insufficient permissions"Caller's role/branch doesn't match the rule, or the query isn't branch-scoped. Confirm the user's role/status and the read guard.
A write "silently" fails from the clientThat collection is functions-only (write:false). Call the matching callable instead of writing directly.
Web build fails on a new fieldRebuild @stockmate/types first; web/functions consume the compiled package.
PowerShell: && not recognizedChain commands with ; on PowerShell.
Deploy: "Quota exceeded … mutation requests"Transient per-minute function-update limit; the CLI retries — re-run if needed.
Android doesn't show new fieldsRebuild the APK; the app isn't compiled by the web toolchain.
